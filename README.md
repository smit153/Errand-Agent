# Errand Agent

A local, chat-based agent that arranges home-service errands: it clarifies missing details,
compares providers, asks for approval before consequential actions, and recovers safely from tool
failures. The errand path runs locally with mock providers; there are no real errand providers or
payments. The language model is reached through a local ModelMux gateway (see [Language model](#language-model)). The brief is the company's assignment document (not included here); the design is
[docs/DESIGN.md](docs/DESIGN.md), with decisions and the build plan in
[docs/DECISIONS.md](docs/DECISIONS.md).

## Status

All 8 stages of the build plan ([docs/DECISIONS.md §15](docs/DECISIONS.md)) are done:

1. PostgreSQL 16 + pgvector schema, migrations, test harness, durable claims with generation fencing.
2. All eight fixed mock tools with seeded, configurable failure behaviour.
3. The code-enforced approval gate, the operation executor (exact-snapshot dispatch, forced
   source-of-truth verification, same-key retries, limits) and crash recovery.
4. The conversational agent with guardrails G1–G11: state-scoped, enum-constrained tool calls,
   code-resolved dates and ranking, code templates for every consequential message, grounding
   checks, untrusted-data isolation, bounded retries and a degraded menu, all tested offline with
   a scripted model.
5. Persistent memory (explicit vs inferred, inspect/correct/forget) and context management: a fixed
   4,096-byte context cap with a drop order, relevance-ranked memories behind SQL hard filters, and
   a hostile 50+ memory seed that proves only relevant, current, confirmed facts reach the model.
6. Background work: a Postgres job queue (`SKIP LOCKED`, leases) for durable dispatch, the
   cancel-503 retry and verification follow-ups; a provider-cancellation watcher that finds a
   replacement within the user's constraints and asks for fresh approval; an outbox for
   notifications (at-least-once, stable IDs).

7. Evidence: JSONL trace export, a real timeout-after-success trace, an eval table generated by
   the test run, and a one-page design note.

8. A local HTTP API (loopback, one local user, request de-duplication) and a thin terminal client
   with a live trace pane and notifications.

## Setup

Requirements: Docker with Compose. The Python 3.12 toolchain runs in a container, so no local
Python install is needed.

```bash
cp .env.example .env            # then set ERRAND_DB_PASSWORD to a random value
docker compose up -d --wait postgres
docker compose --profile dev build dev
scripts/dev.sh scripts/check.sh # hash-verified install, ruff, mypy --strict, pytest
```

Postgres listens on `127.0.0.1:5433` only. Tests create and drop their own `errand_test` database
on that server. Pass pytest arguments through, e.g. `scripts/dev.sh scripts/check.sh -k approval`.

## Dependencies, the package mirror and hash verification

Images and packages are pinned:

- **Images** are pinned by digest: `pgvector/pgvector:0.8.1-pg16` (PostgreSQL 16.12) and
  `python:3.12-slim-bookworm` (Python 3.12.16).
- **Python packages** are pinned in `requirements.lock` (runtime) and `requirements-dev.lock`
  (runtime + dev). Every entry has sha256 hashes, and every install uses `--require-hashes`. The
  uv bootstrap in the dev image is hash-pinned too (`docker/uv-requirements.txt`).

On the machine this was built on, downloads from PyPI's CDN (`files.pythonhosted.org`) ran at about
9 KB/s. So, with the developer's approval, packages were downloaded from the **Tencent PyPI mirror**
(`https://mirrors.cloud.tencent.com/pypi/simple/`). A mirror is safe here only because of the
hashes:

- `scripts/verify_lock_hashes.py` checks every hash in both lock files against PyPI's own JSON
  metadata on `pypi.org`. On 2026-11-07 it checked all 31 pinned packages with 0 failures. A
  mirror cannot substitute a file, because an altered file fails `--require-hashes`.
- The mirror URL appears only in the local, git-ignored `.env` (`PIP_INDEX_URL`,
  `UV_DEFAULT_INDEX`). The committed config defaults to `https://pypi.org/simple`, so on a normal
  network nothing needs changing.

To change dependencies, edit `pyproject.toml`, then re-lock and verify before installing:

```bash
scripts/dev.sh scripts/lock.sh
python3 -I scripts/verify_lock_hashes.py requirements.lock requirements-dev.lock   # must report 0 failures
```

## Language model

The real model is reached through the developer's own [ModelMux](https://github.com/smit153/modelmux/)
gateway: a local, OpenAI-compatible Chat Completions server fronting **Claude Code** (`claude`,
port 8101) or **Codex** (`codex`, port 8102), selected with `ERRAND_MODELMUX_PROVIDER`. This
replaced the original local-Ollama plan by the developer's decision (DECISIONS §17). Setup:
[docs/MODELMUX.md](docs/MODELMUX.md).

- **Locality, and its caveat.** ModelMux and the whole errand path run on this machine; errand
  providers and payments are mocked in-process. The model itself runs on Anthropic's or OpenAI's
  servers under the developer's login. The assignment says the system must run "without real
  providers, payments, or external service integrations"; this project reads that as covering
  errand providers, payments and third-party service APIs, not the LLM. A reviewer may read it
  differently.
- **Offline evaluation.** Automated tests never call a real model; they use a scripted model.
- **Determinism.** ModelMux ignores `temperature`, `seed` and `max_tokens`; they are sent anyway, and
  the ignored list is recorded in every model-call trace. Real-model runs are therefore not seeded.
- **Smoke test.** After `modelmux login claude` (or `codex`) in your own terminal, run
  `scripts/smoke.sh claude`. It runs the three example requests from the brief and writes a report to
  `artifacts/smoke/`. The script reads the gateway key from `~/.config/modelmux/secrets.env` and passes
  it by environment variable; it is never committed, logged or traced.
- **Measured so far.** Codex (`gpt-6.1-sol`), two runs on 2026-11-07: 3/3 flows completed, 24/24 tool
  calls valid on the first attempt, no booking without approval, median call latency about 5.5 s.
  Claude has not been measured yet.

## Running the app

Everything runs on this machine; the API binds to `127.0.0.1` only.

```bash
docker compose up -d --wait postgres
docker compose --profile embed up -d --wait ollama        # optional: memory/embeddings (see below)
modelmux up && modelmux login codex                        # once; your own ModelMux gateway
scripts/serve.sh codex --db errand_demo --fresh --demo-controls --seed-memories
```

`serve.sh` applies migrations, seeds the mock providers, starts the HTTP API with a background
worker, and uses the real model through ModelMux (the gateway key is read from ModelMux's own
secrets file and passed by environment). Then, in two terminals side by side (any Python 3.12+,
no install, standard library only):

```bash
python3 -m errand_agent.cli chat               # the conversation; notifications appear as they arrive
python3 -m errand_agent.cli trace --follow --new-only   # live trace of every new run (omit --new-only to print the history first)
```

`--demo-controls` adds endpoints that steer the mocks for a demo
(`python3 -m errand_agent.cli demo next-booking timeout_booked`, `demo provider-cancel BK-…`,
`demo bookings`); without the flag they don't exist. HTTP endpoints: `POST /sessions`, `POST /sessions/{id}/messages`
(`text`, `client_message_id`, optional `receipt_id`; a retried ID replays the stored reply),
`GET /sessions`, `GET /trace`, `GET /sessions/{id}/trace`, `GET /notifications`,
`POST /notifications/ack`, `GET /health`.

## Background worker

```bash
scripts/dev.sh python -m errand_agent.db.migrate        # once per schema change
scripts/dev.sh python -m errand_agent.workers           # loop; --once for a single tick
```

The worker ingests provider-cancellation events, runs due jobs (retries, verification
follow-ups, crash recovery) and writes user notifications to the outbox. It uses no language
model, holds no state of its own, and several can run at once. It refuses to start if migrations
are pending.

## Memory and embeddings

Saved preferences (preferred area, earliest acceptable time, a preferred provider per service,
short notes) are stored in PostgreSQL with their pgvector embeddings in the same row. Embeddings
come from a local [Ollama](https://ollama.com) running only `nomic-embed-text:v1.5`; chat stays on
ModelMux. Automated tests never need Ollama: they use deterministic or recorded fixture vectors.

```bash
docker compose --profile embed up -d --wait ollama                      # image pinned by digest (3.4 GB once)
docker compose exec ollama ollama pull nomic-embed-text:v1.5            # ~274 MB once; then fully offline
docker compose exec ollama ollama list                                  # copy the model digest into .env:
# ERRAND_EMBED_DIGEST=<full sha256>  (a different installed build is then refused)
```

Users manage memory with plain commands that never go to the model: `show memories`,
`forget memory 3`, `forget my area`, `confirm memory 2` (for a suggestion learned from bookings),
`correct memory 1: Koramangala`. "Remember …" in a normal message saves a preference only when the
user's own words ask for it.
